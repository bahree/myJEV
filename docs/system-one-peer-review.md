# System One architecture and calibration: a source-checked comparison

Reviewed October 6, 2026. This note separates published interfaces, mathematical properties and measurements in myJEV. It does not claim to reproduce TypeSafe's proprietary Jev architecture or training recipe. Product documentation can change; pin a version when evaluating a hosted service.

## Claims, corrections and implementation

| Claim or question | Correction from primary sources | What myJEV implements |
|---|---|---|
| Who makes Jev? | Jev is TypeSafe AI's product. System One is its decision-model framing. The official announcement does not identify a specific pretrained backbone or disclose enough architecture to reproduce it. [Announcement](https://typesafe.ai/blog/introducing-system-one-models-and-jev) | An independent educational implementation, with Qwen adaptation and a separate random-initialization track. It is not official Jev or a verified architectural clone. |
| Is “Noul” a typo for null or a boolean? | **Noul** is the actual API primitive. It returns a number interpreted as the probability of yes. It is not JSON null, a hard boolean or a degree-of-severity score. [Noul documentation](https://docs.typesafe.ai/primitives/noul) | One selected candidate plus scores and reported correctness confidence. There is no implementation of TypeSafe's complete Choice/Score/Noul API. |
| Does a typed result prevent mistakes? | Constraining the output type prevents some structural failures; it does not make the selected value factually correct. TypeSafe itself distinguishes group calibration from individual correctness. [System One documentation](https://docs.typesafe.ai/concepts/system-one) | Schema validation, candidate masks and input limits constrain outputs. Held-out labels still reveal confident errors. |
| Does “no generated text” rule out an LLM backbone? | Output interface and pretraining architecture are different decisions. A network pretrained for next-token prediction can supply representations for a direct classification readout. This does not establish what proprietary Jev uses. | Qwen makes one backbone forward pass and reads candidate token scores; there is no autoregressive answer-generation loop. The backbone still consumes memory and computation. |
| Are token limits and latency universal properties? | TypeSafe currently lists Jev 1.13 at 64k aggregate request tokens and 32k for state plus the longest question. Its launch announcement advertises 70-500 ms end-to-end responses. These are versioned provider specifications/claims, not measurements of every workload or model. [Model limits](https://docs.typesafe.ai/models), [launch claims](https://typesafe.ai/blog/introducing-system-one-models-and-jev) | Artifact-specific tested limits and local model/HTTP timings. We do not inherit those capacities, parallel-question semantics or speed claims. |
| Is every field named confidence a correctness probability? | TypeSafe's current Choice confidence is a derived concentration statistic: `(p_max - 1/n)/(1 - 1/n)`. It is not a separately learned correctness head. Noul has no separate confidence. [Confidence formulas](https://docs.typesafe.ai/confidence) | Native scalar and RL policy heads estimate selected-answer correctness. The default supervised release instead uses temperature-scaled selected-option probability. All are evaluated explicitly; their common range does not make their meanings identical. |
| Is Brier proper while cross-entropy is not? | Both categorical logarithmic loss (cross-entropy against observed labels) and Brier are strictly proper scoring rules at the population optimum. Finite data, misspecification, optimization, regularization and shift can still produce miscalibration. [Gneiting and Raftery](https://sites.stat.washington.edu/people/raftery/Research/PDF/Gneiting2007jasa.pdf) | Cross-entropy supervision, correctness losses, temperature calibration and matched reward controls. The combined answer/confidence reward plus KL has no blanket calibration guarantee. |
| Would focal loss guarantee calibration? | Standard focal loss with positive focusing parameter is not strictly proper in general, even though it can improve empirical calibration in some settings. Classification consistency and calibrated probabilities are distinct properties. [Original analysis and proof](https://openaccess.thecvf.com/content/CVPR2021/supplemental/Charoenphakdee_On_Focal_Loss_CVPR_2021_supplemental.pdf) | Focal loss is not implemented or evaluated here. It is not added merely because a peer suggestion mentions it. |
| Is contrastive InfoNCE training the same as JEPA? | InfoNCE distinguishes a positive target from negatives; I-JEPA predicts target representations from context and uses a different noncontrastive setup. Both learn representations, but neither name implies calibrated class probabilities. [CPC/InfoNCE](https://arxiv.org/abs/1807.03748), [I-JEPA](https://arxiv.org/abs/2301.08243) | Neither objective is part of this study. Cosine similarity or softmax-normalized similarity alone would require separate probability evaluation before being reported as correctness confidence. |
| Does conformal prediction give a guarantee for this individual answer? | Standard split conformal prediction gives marginal prediction-set coverage under exchangeability of calibration and future examples. It does not generally give conditional coverage for every input, an individual correctness probability or a production accepted-error guarantee under shift. [Angelopoulos and Bates](https://arxiv.org/abs/2107.07511) | Calibration-selected acceptance thresholds, empirical accepted error and uncertainty intervals. No conformal predictor or conformal guarantee is claimed. |

## Why the smaller-model comparison matters

A pretrained encoder is not equivalent to a randomly initialized small model. The bounded 149.7M ModernBERT control reached **90.78% BANKING accuracy** and **0.0555 calibrated correctness Brier** after three epochs. Its fixed 77-label head cannot become an arbitrary new classifier by supplying different candidate descriptions alone. The scratch BANKING diagnostic collapsed to **1.30% accuracy**; its low correctness Brier reflected honestly predicting failure, not useful routing. Different pretraining, exposure and interfaces prevent a causal architecture ranking. See the [encoder report](https://github.com/bahree/myJEV/blob/main/results/encoder-control-v1/report.md) and [scratch failure](https://github.com/bahree/myJEV/blob/main/results/scratch-banking-diagnostic/report.md).

For a stable taxonomy, the encoder and TF-IDF controls challenge the need for a large backbone. Dynamic candidates justify additional cost only where measured transfer supports it. Our [SST-2 follow-up](https://github.com/bahree/myJEV/blob/main/results/sst2-transfer-v1/report.md) supplies one bounded human-labelled transfer example, not a universal guarantee.

## A concrete probability distinction

For three candidates with probabilities `[0.6, 0.3, 0.1]`, the maximum probability is 0.6, while TypeSafe's published Choice statistic is 0.4. Neither number becomes a separately trained probability of correctness merely by being returned under `confidence`. myJEV's native head could return a third number. Evaluate the exact deployed quantity, its calibration population and its decision threshold; do not substitute one formula for another without revalidation.

When comparing another decision model, first identify what its probabilities mean and which data it has seen. Then choose a task on which both systems can be evaluated. The [architecture](architecture.md), [decision lessons](decision-lessons.md) and [experiments](experiments.md) document those choices for myJEV.
